# Legacy feature preservation audit

25 October 2026. Production baseline: `main` **abae7f8779f101848309b1ce12090da3da1e8742**; audited Phase 1B candidate: **c58745ac40bc370042d5746d88ccb711a1cdb0f8**. Same repository/history; no production, hosting, database or integration change. This audit adds documentation and regression tests only. Editorial source, the 16 approved service pages, premium design and all assets remain untouched.

“Production behavior” below means behavior implemented by the pinned production **source**, not an assertion that its deployed environment, credentials, records or traffic were tested. The baseline was inspected with `git show`/`git ls-tree`, never executed with live configuration. Current isolated localhost GETs checked shortcuts, their destinations, Preview indexing endpoints and signed-out admin routing. Existing Neon intermittency remains open; passing compatibility tests do not clear it.

## High-value functionality that could be forgotten

1. Printed `/huduma` and `/whatsapp` shortcuts, including correct Kiswahili and the owner-approved WhatsApp number. They survive; the old WhatsApp destination/label inconsistency must not return.
2. Product/package/service context carried into the site-survey form, its reference-bearing success URL, and the private admin follow-up queues. These are commercial workflows, not merely contact-page decoration.
3. The six support-guide slugs and CCTV package detail URLs. Replacing the homepage must not silently orphan useful resource links or verified published records.
4. Saved product images, project photos/location/category and related-record discovery. Some premium views currently omit these stored fields; restore verified content within the approved design before claiming complete presentation parity.
5. Optional survey budget: original selector is absent from the premium form, although validation, storage and admin display still support it. Owner should decide whether to restore an optional field; no change made now.
6. SMS office alerts and admin OTP are actual server-side integrations. WhatsApp/email are contact links, not messaging APIs. An old comment about appointment alerts does not make appointment booking operational.
7. `/admin/settings` is currently a read-only configuration display, with an explicit future editable-settings intention. Do not claim staff can already update contacts there.
8. Core service admin field ownership: source-managed premium titles/intro/features/imagery do not all follow saved CMS edits. Publication control and supplemental CMS content survive; clarify this contract before staff rely on the editor.
9. Published/draft control and safe fallbacks: a deliberately withdrawn service/article must not reappear from static data. Removing unverified product/project/package examples is an intentional correctness improvement. A database error is not a missing-record signal: current service/support lookups do not catch it and silently republish fallback content.

See [all route/redirect contracts](ROUTE-AND-REDIRECT-COMPATIBILITY.md) and [integration/admin status and backlog](INTEGRATION-AND-ADMIN-BACKLOG.md).

### Recommended authoritative structure (proposal only)

Keep one typed **public business configuration** rooted in `data/site.ts`: identity and explicit canonical origin; `contacts.sales`; `offices.moshi` and `offices.arusha` with structured verified address/telephone; WhatsApp referencing the Moshi contact; optional verified social/hour settings. Derive `phones`, legacy `location` aliases, formatted labels, tel links, wa.me destination and schema facts from these records rather than editing independent copies. Keep `data/service-divisions.json` and the existing service registry authoritative for service navigation, not the stale six-string siteConfig.services list.

A pure contact-link function should accept an explicit Preview policy and serve both Next redirect configuration and components; it must not import Prisma, a settings database or server secrets into client/build configuration. Preserve runtime notification suppression as a separate enforcement layer. Canonical origin is distinct from a display domain; no host migration is implied.

Keep **private runtime configuration** separate: provider credentials, allowed admins/session policy, notification-recipient override and database identity come from scoped server environment only. A later `/admin/settings` editor may manage validated public settings via the existing SiteSetting model, with authorisation, revision/audit, cache invalidation and approved fallback. It must not edit secrets or automatically change SMS recipients. That future intention already appears in `data/site.ts` and the settings page; no editor or new integration was built now.

## Verification and remaining boundaries

No app/configuration changes required, so the production-mode build was not rerun for documentation/tests alone. Local destinations confirmed the SW directory (including the three priority security links), the bilingual disabled-notification notice, noindex headers, disallow-all robots and an empty sitemap. Six new hermetic compatibility tests cover all baseline route patterns, both shortcut policies, central WhatsApp agreement, survey context/locale, appointment honesty, support slugs and independent notification-suppression flags. Existing suites cover authorisation, publication, metadata, receipt deduplication and provider suppression. No Production data or credential values were read.
